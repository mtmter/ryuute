# Ryuute

「予定」だけでなく、**その予定に間に合うために必要な移動時間まで管理する**Webスケジュール帳です。

通常の予定・タスク管理に加えて、予定の場所から経路を検索し、移動時間を予定の直前に組み込んで表示します。

例えば10:30開始の予定へ向かうのに1時間必要なら、カレンダー上では次のように扱います。

```text
09:20 - 10:20  移動
10:30 - 12:00  予定
```

「10:30に予定がある」だけではなく、**「09:20には移動を始める必要がある」**ところまで分かることがRyuuteの中心機能です。

---

# 1. 2026-08-24時点の方針

このREADMEを今後の実装仕様の基準とします。

現在のリポジトリにはReact / FastAPI / SQLiteによる予定・タスク管理、予定詳細、経路検索UI、TravelPlan API、準備チェックリスト・準備案内などが実装されています。

一方、バックエンドの経路検索サービスにはGoogle Routes APIを利用した既存実装が残っています。日本の公共交通経路取得で期待した結果を安定して得られなかったため、**経路検索の本番APIを駅すぱあと API スタンダードへ変更**します。

また、場所入力にはGoogle Places Autocompleteを利用し、予定詳細からGoogle Mapsを開けるようにします。

最終デモでは外部の経路API接続に依存してデモ全体が失敗しないよう、**駅すぱあとのレスポンス構造を模したMock JSON**をバックエンドで読み込み、本番時と同じアプリ用JSONへ変換して返します。

```text
場所入力          Google Places Autocomplete
地図リンク        Google Maps URLs
公共交通経路検索  駅すぱあと API スタンダード
デモ経路          駅すぱあと形式のMock JSON
```

Google Routes APIは新仕様では経路検索に使用しません。

# 3. アプリの主要機能

## 3.1 カレンダー

以下の表示を用意します。

- 月表示
- 週表示
- 日表示
- タスク表示

### 月表示

1か月分の予定を表示します。

日付セルをクリックすると、その日を初期値とした予定追加モーダルを開きます。

### 週表示

1週間分の予定を時間軸上に表示します。

通常予定に加えて、登録済みの移動予定も時間ブロックとして表示します。

```text
09:00

09:20 ┌────────────────┐
      │ 移動            │
      │ -> Garraway F   │
10:20 └────────────────┘

10:30 ┌────────────────┐
      │ ハッカソン      │
      │ Garraway F      │
12:00 └────────────────┘
```

空いている時間帯をクリックすると、その日時を初期値とした予定追加モーダルを開きます。

### 日表示（Issue #58）

既存の月表示、週表示、タスク表示を残したまま、表示切り替えに「日」を追加します。「日」は既存の「週」と「タスク」の間に配置し、既存ボタンの役割や操作は変更しません。

日表示では、選択した1日を週表示と同じ24時間の時間軸上に1列で表示します。日表示のために新しい予定データを保存せず、起動時に既存APIから取得済みの予定とタスクをReact内で対象日のみに絞り込みます。

#### 表示内容

- ヘッダーには選択日を `YYYY年M月D日（曜日）` の形式で表示する
- 時間軸は `00:00` から `24:00` までとし、縦にスクロールして確認できるようにする
- 選択日に重なる予定を、週表示と同じ時間ブロックで表示する
- 選択日が期限の未完了タスクを、時間軸の上にある「期限」欄へ表示する
- 期限タスクは期限時刻が早い順に並べ、期限時刻とタイトルを表示する
- 期限がないタスク、選択日以外が期限のタスク、完了済みタスクは日表示の「期限」欄へ表示しない
- 予定と期限タスクが0件の場合も、選択日の時間軸と「期限」欄は表示する

複数日にまたがる予定は、選択日に重なる部分だけを `00:00` から `24:00` の範囲内へ表示します。予定の並び順、短い予定の最小表示高さ、同じ時間帯に予定が重なった場合の扱いは、既存の週表示と同じにします。日表示専用の重複調整機能は追加しません。

#### 日付移動と表示切り替え

- 既存ヘッダーの「今日」を選択すると、今日の日表示へ移動する
- 既存ヘッダーの前へ・次へボタンでは、選択日を1日ずつ移動する
- 月表示または週表示から日表示へ切り替えた場合は、現在の表示基準日を日表示の選択日として引き継ぐ
- タスク表示から日表示へ切り替えた場合は、最後にカレンダーで選択していた日を表示する
- 日表示から月表示、週表示、タスク表示へ切り替えても、それぞれの既存機能を変更しない

#### 予定とタスクの操作

予定ブロックを選択すると、既存の予定詳細モーダルを開きます。予定の確認、編集、削除、準備チェックリスト、経路検索など、予定詳細から行う既存操作は変更しません。

時間軸の空いている場所を選択すると、週表示と同じ30分単位で開始時刻を決め、その日時を初期値とした予定追加モーダルを開きます。ヘッダーの「追加」を日表示で選択した場合は、選択日の `09:00` を開始時刻、`10:00` を終了時刻とした既存の予定追加モーダルを開きます。

日表示の「期限」欄は週表示と同じ表示専用とし、この欄を選択してタスク詳細やタスク追加を開く新しい操作は追加しません。タスクの追加・完了切り替えなどは、既存のタスク表示で行います。

#### ミニカレンダーと画面配置

画面幅が721px以上では、日表示でも既存の左サイドバーを表示します。ミニカレンダーでは日表示の選択日を強調し、日付を選択すると予定追加モーダルを開かず、その日の日表示へ移動します。ミニカレンダーの前月・次月ボタンは、既存仕様どおりミニカレンダーに表示する年月だけを変更します。

画面幅が720px以下では、既存仕様どおり左サイドバーを表示せず、準備案内を画面上部へ表示します。日表示の時間軸はメイン表示領域内で縦にスクロールできるようにし、ページ全体の既存レイアウトを置き換えません。

#### フロントエンド内での完結

日表示の表示切り替え、日付移動、予定とタスクの絞り込み、時間ブロックの配置はReact内で行います。アプリ起動時などに行う既存の予定・タスク取得はそのまま使用しますが、日表示への切り替えや日付移動を理由とした追加のAPI通信は行いません。

この機能のために、以下は追加・変更しません。

- FastAPIのエンドポイント
- SQLiteのテーブルや保存データ
- 既存APIのリクエスト・レスポンス
- Google Calendarなどの外部サービスとの連携
- 外部APIへの通信
- 新しいライブラリ
- 日表示用の `localStorage` 保存

#### 完了条件

1. 既存の月表示、週表示、タスク表示を残したまま「日」を選択できる
2. 日表示で選択した1日の `00:00` から `24:00` までを1列の時間軸で確認できる
3. 選択日に重なる予定だけが正しい時間帯に表示される
4. 複数日にまたがる予定は、選択日に重なる範囲だけが表示される
5. 選択日が期限の未完了タスクが「期限」欄へ期限時刻順に表示される
6. 予定や期限タスクがない日も、時間軸と「期限」欄が表示される
7. 予定を選択すると既存の予定詳細モーダルが開く
8. 空いている時間帯を選択すると、その日時を初期値とした既存の予定追加モーダルが開く
9. 「今日」と前へ・次へボタンで、今日または前日・翌日へ移動できる
10. 月表示・週表示・タスク表示との切り替えで、表示基準日が仕様どおり引き継がれる
11. 画面幅が721px以上では、ミニカレンダーの日付選択でその日の日表示へ移動できる
12. 画面幅が720px以下でも、既存の上部表示を崩さず日表示を操作できる
13. 日表示の切り替えや日付移動による追加のAPI通信が発生しない
14. API、DB、外部サービス、依存ライブラリ、`localStorage` の仕様が増えていない
15. 既存の月表示、週表示、タスク表示、予定・タスク操作、準備案内、経路検索が従来どおり動作する

### タスク表示

タスクを一覧表示し、未完了と完了済みを分けて扱います。

# 4. 予定機能

## 4.1 予定追加

予定追加モーダルは以下から開きます。

- ヘッダーの「追加」
- 月カレンダーの日付
- 週カレンダーの空き時間

予定には以下の情報を持たせます。

| 項目 | 必須 | 説明 |
| --- | --- | --- |
| `title` | 必須 | 予定タイトル |
| `start_at` | 必須 | 開始日時 |
| `end_at` | 必須 | 終了日時 |
| `description` | 任意 | 説明 |
| `location_name` | 任意 | ユーザーへ表示する場所名 |
| `destination` | 任意 | 住所。経路検索のフォールバックにも使用 |
| `destination_place_id` | 任意 | Google Place ID |
| `destination_lat` | 任意 | 緯度 |
| `destination_lng` | 任意 | 経度 |
| `arrival_buffer_minutes` | 任意 | 予定開始何分前までに到着したいか |

日時はアプリ内では `YYYY-MM-DDTHH:mm` のローカル日時として扱います。

`arrival_buffer_minutes` が未設定の場合は、経路検索時に0分として扱います。

# 5. 場所入力とGoogle Places Autocomplete

## 5.1 基本仕様

場所入力にはGoogle Places Autocompleteを使用します。

Autocompleteは以下で共通利用します。

- 予定追加時の場所入力
- 予定編集時の場所入力
- 経路検索時の出発地入力

入力中は候補を表示し、ユーザーが候補を選択した場合は最低限次の情報を取得します。

```text
name
address
place_id
lat
lng
```

予定では次のように保存します。

```text
name      -> events.location_name
address   -> events.destination
place_id  -> events.destination_place_id
lat       -> events.destination_lat
lng       -> events.destination_lng
```

## 5.2 手入力の扱い

Autocomplete候補を選択しなくても通常予定として保存できるようにします。

候補を選択していない場合は、入力文字列を `location_name` または `destination` として保存できます。

ただし、経路検索では座標がある方が安定するため、経路検索を利用する予定についてはAutocomplete候補の選択を推奨します。

経路検索時は次の優先順位で地点を決定します。

```text
1. 緯度・経度
2. 住所文字列
```

# 6. Google Mapsリンク

予定詳細では、場所が設定されている場合にGoogle Mapsを開けるようにします。

URL自体はDBへ保存せず、表示時に生成します。

Place IDがある場合は、Google Maps Search URLの `query_place_id` を使用して対象施設をできるだけ一意に開きます。

Place IDがない場合は、場所名または住所だけを `query` に使用します。

Google Maps URLを開くためのAPIキーは不要です。

# 7. 予定詳細

予定をクリックすると予定詳細モーダルを表示します。

予定詳細では以下を行います。

- 予定内容の確認
- 場所からGoogle Mapsを開く
- 予定の編集
- 予定の削除
- 準備チェックリストの確認・追加・編集・削除
- 準備項目の完了状態の切り替え
- 登録済み移動予定の確認
- 経路検索
- 経路再検索

場所に経路検索可能な情報がない予定では、経路検索ボタンを表示しない、またはdisabledにします。

# 8. 経路検索

## 8.1 入口

主なフローは次のとおりです。

```text
カレンダー
   ↓
予定をクリック
   ↓
予定詳細
   ↓
「経路を検索」
   ↓
経路検索モーダル
```

## 8.2 出発地

出発地はユーザー設定として保存しません。

経路検索のたびに入力し、Google Places Autocompleteから選択できます。

出発地をDBやlocalStorageへ保存する設定機能は設けません。

## 8.3 到着希望日時

到着希望日時はバックエンドで計算します。

```text
desired_arrival_at
= event.start_at - event.arrival_buffer_minutes
```

`arrival_buffer_minutes` が `null` の場合は0分です。

# 9. Route Search API

## 9.1 Endpoint

```http
POST /api/events/{event_id}/route-search
```

## 9.2 Request

```json
{
  "origin_name": "九州大学 伊都キャンパス",
  "origin_address": "福岡県福岡市西区元岡744",
  "origin_place_id": "GOOGLE_PLACE_ID",
  "origin_lat": 33.596,
  "origin_lng": 130.215
}
```

`origin_place_id` は駅すぱあとへ直接送信しません。

経路探索には主に `origin_lat` / `origin_lng` を使用します。

座標がない場合は `origin_address`、それもなければ `origin_name` をフォールバックとして利用します。

目的地はEventから取得します。

## 9.3 バックエンド処理

```text
POST /api/events/{event_id}/route-search
        ↓
Event取得
        ↓
目的地取得
        ↓
予定開始 - 到着余裕時間
        ↓
desired_arrival_at
        ↓
Route Provider
        ↓
駅すぱあと形式レスポンス
        ↓
convert_ekispert_route()
        ↓
アプリ共通Route JSON
        ↓
React
```

検索しただけではTravelPlanを保存しません。

# 10. 駅すぱあと API スタンダード

公共交通の検索には `GET /v1/json/search/course/extreme` を使用します。

主なパラメータ：

```text
key=<EKISPERT_API_KEY>
viaList=<出発地点>:<目的地点>
gcs=wgs84
date=YYYYMMDD
time=HHMM
searchType=arrival
answerCount=1
sort=ekispert
```

MVPでは1件の経路だけを表示するため `answerCount=1` とします。

予定へ間に合う経路を検索するため `searchType=arrival` を使用します。

Google Placesから取得した緯度経度はWGS84として扱い、駅すぱあと側でも `gcs=wgs84` を指定します。

## 10.1 徒歩区間について

駅すぱあとへ座標を指定した場合、座標から最寄り駅までの移動時間は実際の道路経路ではなく概算です。

MVPでは次の仕様とします。

```text
鉄道・公共交通のダイヤ  -> 駅すぱあと
施設 <-> 最寄り駅の徒歩 -> 駅すぱあとによる概算
```

# 11. Route Provider

外部API固有処理をフロントエンドやFastAPIのEndpointへ直接埋め込まないため、経路取得処理をProviderとして分離します。

```text
backend/
├── main.py
├── database.py
├── routes_service.py
├── route_providers/
│   ├── mock_provider.py
│   └── ekispert_provider.py
└── fixtures/
    └── ekispert_route_demo.json
```

実際のファイル分割は変更して構いませんが、責務は分離します。

```text
Mock Provider
    ↓
駅すぱあと形式Mock JSON
    ↓
convert_ekispert_route()
    ↓
アプリ共通JSON
```

```text
Ekispert Provider
    ↓
駅すぱあと API
    ↓
駅すぱあと生JSON
    ↓
convert_ekispert_route()
    ↓
アプリ共通JSON
```

**Mockでも本番でも、変換処理より後ろは同じコードを使います。**

# 12. デモ用Mock JSON

デモ用Mockは、アプリ共通JSONを直接返すのではなく、**駅すぱあとの生レスポンスのうちアプリで利用する構造を模したfixture**とします。

想定ファイル：

```text
backend/fixtures/ekispert_route_demo.json
```

デモケース：

```text
出発地: 九州大学 伊都キャンパス
目的地: Garraway F
```

駅すぱあとのJSONでは、要素数によって同じキーが単一オブジェクトまたは配列になる場合があるため、変換処理側で正規化して扱います。

```python
def as_list(value):
    if value is None:
        return []
    if isinstance(value, list):
        return value
    return [value]
```

# 15. 移動予定 TravelPlan

移動予定は通常予定とは別の `travel_plans` テーブルへ保存します。

1つの予定につき1件とします。

# 16. DB共通仕様

SQLiteを使用します。

日時はMVPでは次の文字列形式で保存します。

```text
YYYY-MM-DDTHH:mm
```

使用するテーブルは次の4つです。

```text
events
tasks
travel_plans
event_preparations
```

出発地点を保存する `settings` テーブルは使用しません。

# 17. eventsテーブル

# 21. 準備チェックリスト・準備案内

## 21.1 準備チェックリスト

予定詳細モーダルに準備チェックリストを表示します。

準備項目は以下を操作できます。

- 追加
- 編集
- 削除
- 完了 / 未完了切り替え

準備項目が0件の場合も、予定詳細モーダルには準備チェックリスト欄と追加ボタンを表示します。

## 21.2 準備案内の対象

次の条件をすべて満たす予定を準備案内へ表示します。

- 予定の開始日時が現在時刻より後である
- 予定開始までの残り時間が設定された通知期間以内である
- 未完了の準備項目が1件以上ある

複数の予定が対象になった場合は、開始日時が近い順にすべて表示します。準備案内を選択すると、その予定の予定詳細モーダルを開きます。

すべての準備項目を完了した予定は準備案内から取り除きます。完了状態を未完了へ戻した場合は、ほかの条件も満たしていれば再び表示します。

残り時間は画面を開いたとき、画面へ戻ったとき、設定・予定・準備項目を変更したときに再計算します。画面を開いたままの場合も1分ごとに再計算します。

## 21.3 通知期間

通知期間は全予定共通で以下から選択します。

```text
1時間前
3時間前
1日前
3日前
7日前
```

初期値は3日前です。

設定は `localStorage` に保存します。

## 21.4 アプリ内通知の配置

ブラウザNotifications API、Service Worker、外部通知サービスは使用しません。

画面幅が721px以上の月表示、週表示、日表示では、ミニカレンダーと準備案内を同じ左サイドバー内へ縦に並べます。

```text
┌──────────────────┬──────────────────────────┐
│ ミニカレンダー   │                          │
├──────────────────┤ 既存の月・週・日表示     │
│ 通知1            │                          │
│ 通知2            │                          │
│ 通知3            │                          │
│      ↕            │                          │
└──────────────────┴──────────────────────────┘
```

左サイドバーの高さはメインカレンダーの表示領域を基準とします。ミニカレンダーはサイドバー上部に配置し、その下の準備案内エリアだけを縦スクロールできるようにします。通知件数に応じてページ全体やメインカレンダーの高さを広げません。

タスク表示と画面幅が720px以下の場合は左サイドバーを表示せず、準備案内を従来どおり画面上部へ表示します。通知の内容、表示順、予定詳細を開く操作は変更しません。

## 21.5 ミニカレンダー

月表示、週表示、日表示で目的の日付へ移動しやすくするため、既存のメインカレンダーの左側に補助的なミニカレンダーを追加します。既存のヘッダー、月カレンダー、週カレンダー、日表示、タスク表示、各モーダルは置き換えません。

ミニカレンダーには以下を表示します。

- 表示中の年月
- 前月・次月へ移動するボタン
- 日曜日から土曜日までの曜日
- 表示中の月の日付
- 最初と最後の週に含まれる前月・翌月の日付

日付は日曜日始まりの7列で表示します。前月・翌月の日付は当月の日付より薄い色にします。

現在の日付は常に識別できるようにします。月表示ではメインカレンダーの表示基準日を選択日として強調します。週表示ではメインカレンダーに表示している7日間を強調し、その中の表示基準日をさらに識別できるようにします。日表示では表示している1日を選択日として強調します。現在の日付と選択日が同じ場合も、両方の状態が分かる表示にします。

ミニカレンダーの日付部分には、予定名、タスク名、件数、準備項目、移動予定を表示しません。準備案内は日付部分の中ではなく、ミニカレンダーの下にある独立したエリアへ表示します。

## 21.6 ミニカレンダーの操作

ミニカレンダーの日付を選択した場合は、予定追加モーダルを開かず、メインカレンダーの表示期間だけを移動します。

- 月表示では、選択した日を含む月へ移動する
- 週表示では、選択した日を含む週へ移動する
- 日表示では、選択した日へ移動する
- 前月・翌月の日付を選択した場合も、その日付を基準に移動する

ミニカレンダー内の前月・次月ボタンは、ミニカレンダーに表示する年月だけを変更します。この操作だけではメインカレンダーの表示期間を変更しません。

既存ヘッダーの「今日」、前へ、次への操作でメインカレンダーの表示期間が変わった場合は、ミニカレンダーもメインカレンダーの表示期間を含む月へ同期します。

既存のメインカレンダーの日付セルを選択したときに、予定追加モーダルを開く動作は変更しません。

## 21.7 フロントエンド内での完結

ミニカレンダーの日付生成、月の移動、選択日の管理、強調表示、準備案内の配置切り替えはReact内で行います。

この機能のために、以下は追加・変更しません。

- FastAPIのエンドポイント
- SQLiteのテーブルや保存データ
- 既存APIのリクエスト・レスポンス
- Google Calendarなどの外部サービスとの連携
- 外部APIへの通信
- 新しいライブラリ
- ミニカレンダー用の `localStorage` 保存

ミニカレンダーの日付部分には予定・タスクなどのAPI取得結果を使用しません。既存データの取得に失敗した場合も、日付ナビゲーション自体は表示できるものとします。

準備案内のデータ取得と対象判定には既存の処理を使用し、表示位置の変更のための新しいAPIや保存処理は追加しません。

## 21.8 完了条件

1. 画面幅が721px以上の月表示、週表示、日表示で、既存カレンダーの左側にミニカレンダーと準備案内のサイドバーが表示される
2. サイドバー内でミニカレンダーの下に準備案内が表示される
3. サイドバーに収まらない準備案内を、準備案内エリア内で縦スクロールして確認できる
4. 通知件数が増えても、メインカレンダーの表示領域が縦方向に圧迫されない
5. タスク表示と画面幅が720px以下では左サイドバーが表示されず、準備案内が画面上部に表示される
6. 年月、曜日、当月の日付、前月・翌月の日付が正しく表示される
7. 現在の日付と、メインカレンダーで表示中の日付または期間を識別できる
8. ミニカレンダーの前月・次月ボタンで、ミニカレンダーだけの表示月を変更できる
9. 月表示で日付を選択すると、その日を含む月へ移動する
10. 週表示で日付を選択すると、その日を含む週へ移動する
11. 日表示で日付を選択すると、その日へ移動する
12. ミニカレンダーの日付を選択しても予定追加モーダルが開かない
13. 既存ヘッダーによる日付移動がミニカレンダーにも反映される
14. 表示位置の変更のためのAPI通信、DB変更、外部サービス連携が発生しない
15. 既存の月表示、週表示、日表示、タスク表示、予定・タスク操作、準備案内、経路検索が従来どおり動作する
